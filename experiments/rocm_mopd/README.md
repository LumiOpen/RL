# Native multi-teacher OPD on AMD ROCm

**Complete; closed October 6, 2026.** Both the routed math/coding arm and the
single-teacher control completed 50 updates, export validation, evaluation and
grading. The final Slurm controller finished automatically on October 3, with
no retries. No further training is scheduled.

The full experiment record is [MOPD_RECIPE.md](../../MOPD_RECIPE.md). It documents
models, data selection, inherited optimizer/loss settings, runtime fixes,
validation, results and limitations. [final_results.json](final_results.json)
is the compact final record; [extension_50_results.json](extension_50_results.json)
contains paired comparisons and confidence intervals.

## Result

| Model | Coding, 700 samples | Math, 120 samples | Coding truncation |
|---|---:|---:|---:|
| SFT baseline | 33.71% | 59.17% | 31.14% |
| Single teacher, 20 updates | 34.71% | 55.83% | 28.71% |
| MOPD, 20 updates | 34.14% | 60.00% | 34.71% |
| Single teacher, 50 updates | 35.14% | 54.17% | 38.00% |
| MOPD, 50 updates | 33.71% | 55.00% | 42.71% |

Native MOPD execution is validated, but this experiment does not establish a
learning benefit. At 50 updates, MOPD minus control is −1.43 percentage points on
coding (95% interval −3.57 to +0.86) and +0.83 on math (−7.50 to +9.17).
Both intervals include zero. Neither arm met the coding extension gate.
Increasing truncation merits investigation before further training.

The successful historical [single-teacher recipe](../../TM_OPD_RECIPE.md) used
a different adapter continuation, objective/reduction, Adam beta2, clipping and
batch size. The native control shares the native settings, while the routed arm
uses different teacher checkpoints. This is not an isolated teacher-count test.

## Runtime and requirements

Training uses MI325X, `primus_v26.5-pytorch2.12-te2.15.sif`, Python 3.12,
Torch 2.12/ROCm 7.15 and AMD TE 2.15. Bridge/Core/Gym source pins are recorded in
[protocol.json](protocol.json). Gym declares Python 3.13; this source checkout
was validated locally with the image's Python 3.12. Evaluation reuses the
preserved Torch 2.11/ROCm 7.2/vLLM 0.25.1 environment.

First prepare the frozen overlays and site-specific paths in the
[parent setup](../README.md). Populate the model/dataset snapshots offline and
prepare the isolated coding grader as described in the [coding recipe](../coding_opd/README.md).
Do not replace the container's Torch, NumPy or Ray with CUDA/default PyPI builds.

```bash
# From the repository root. Install the added native dependencies in their
# separate environment using the container interpreter.
bash experiments/rocm_sft/container.sh uv --no-config sync --locked --all-extras \
  --project experiments/rocm_mopd/deps --python /opt/venv/bin/python

# Regenerate the portable requirements view from the same lockfile.
uv --no-config export --project experiments/rocm_mopd/deps --locked --all-extras \
  --no-dev --no-hashes --no-emit-project \
  --output-file experiments/rocm_mopd/requirements.txt
```

[requirements.txt](requirements.txt) is a generated view of
[deps/pyproject.toml](deps/pyproject.toml) and [deps/uv.lock](deps/uv.lock), not a
replacement for the container or the existing overlays. `sys_platform == 'never'`
entries deliberately suppress Torch/NumPy/Ray installation. Use `uv sync` above
for the tested runtime layout. The Gym resource's own requirements file declares
`nemo-gym`; the launcher supplies its pinned source and skips installing that
manifest into the job-local server environments.

The separate [grader requirements](../coding_opd/grader/requirements.txt) pin
NumPy 2.2.6 for isolated candidate execution. Never execute generated code in the
training container or on the login node.

## Launch and reproduction

These are frozen TensorWave recipes. Edit absolute model/data/output paths,
W&B account, networking and partition settings before using another cluster.
Submit from the repository root using verification/normal QoS. Each virtual
role has TP=2: eight GPUs for routed training, six for the shared-teacher control.
Allocation-local GPU indices and job-local caches are set by the launcher.

Start with the import and tiny LoRA training audits:

```bash
sbatch --exclude=tus1-p15-g5,tus1-p15-g62 experiments/rocm_mopd/probe.sbatch
NRL_MOPD_CONFIG=experiments/rocm_mopd/native_lora_smoke.yaml \
NRL_MOPD_ENTRYPOINT=experiments/rocm_mopd/audit_native.py \
  sbatch --exclude=tus1-p15-g5,tus1-p15-g62 experiments/rocm_mopd/native_smoke.sbatch
```

For a fresh pilot, use `pilot.yaml`/`pilot_control.yaml`, the audit entry point,
8/6 GPUs, 64 CPUs, 512G RAM and a 12-hour allocation. Their internal deadline is
11h30m; a clean early exit must resume until the saved update count is 20.
The original prompt file is regenerated by `prepare_data.py` from the prepared
math/coding sources, with source indices/hashes in its manifest.

For the 50-update continuation, copy each entire step-20 checkpoint and its
`latest_checkpoint_status.json` to a new run root. Include optimizer, dataloader,
replay and native data-plane state. `extend_*_50.yaml` allows three epochs of the
same 640 prompts and restores the constant checkpoint scheduler. Training uses
24-hour allocations and a 23-hour internal deadline. Do not reuse the completed
run IDs or monitor state for a fresh experiment.

The recorded continuation controller is deliberately tied to its two copied
run roots and the `extend_resume_smoke` preflight. To reproduce its automation,
prepare those roots in a separate checkout, run `extend_resume_smoke.yaml` against
a copied two-step tiny LoRA checkpoint, and call `initialize(new_state_path, preflight_job_id)` from
`monitor_extension.py` once to write the fresh state without starting a foreground
poller. Submit `monitor_extension.sbatch` with its state path updated for the new
experiment. The CLI's `--initialize` option instead creates state and immediately
starts polling in that same process. Existing completed state must not be reset.

After training, the chain executes these stages (shown for update 50):

```bash
# RUN_ROOT must identify the completed, audited continuation.
sbatch experiments/rocm_mopd/export.sbatch --run "$RUN_ROOT" --step 50 \
  --require-probe --validate-merge
# Run only after export validation succeeds:
sbatch experiments/rocm_mopd/evaluate.sbatch "$RUN_ROOT" 50
# Run only after generation completes:
sbatch experiments/coding_opd/grade.sbatch \
  --input "$RUN_ROOT/evaluation_step_50/eval_lcb" --models opd \
  --baseline experiments/coding_opd/run_eval_50305/graded.jsonl
# Run only after both arms have complete summaries:
sbatch experiments/rocm_mopd/report.sbatch "$STATE_PATH" --step 50
```

The controller submits export → evaluation → grading with Slurm dependencies,
then the paired report. It polls every 30 seconds, bounds infrastructure retries,
and detects three hours without a completed training update. Numerical errors,
unknown failures and external cancellations require investigation; it cannot
wake an interactive assistant. Nine focused controller tests and the completed
GPU resume smoke validate its recovery boundaries and artifact selection.
